# 系统事实粒度规范

本文定义 Agent 将材料拆分为 Complai `system_fact` 时的规范粒度。目标是在不同合规
框架和不同年度项目之间复用同一组客观事实，同时让每条事实可以独立验证、更新、
失效和追溯。

本文中的“必须”“不得”“应该”和“可以”分别表示强制要求、禁止要求、默认建议和
可选做法。

## 1. 规范定义

一条系统事实必须是：

> 对一个明确对象，在一个明确范围内，由一个明确来源支撑，并按同一生命周期变化的
> 可独立判真或判假的客观主张。

可用下式检查：

```text
系统事实 = 对象 + 范围 + 客观状态 + 必要机制 + 必要例外 + 来源时间
```

- **对象**：人员账号、服务账号、应用、数据库、网络设备、流程或策略等。
- **范围**：系统、组件、环境、地域、账号群体、数据类别或时间范围。
- **客观状态**：当前真实存在、启用、执行或缺失的状态。
- **必要机制**：解释该状态如何实现所必需的机制，不扩展到独立控制措施。
- **必要例外**：限定主张真实性的例外；拥有独立机制或生命周期的例外另拆事实。
- **来源时间**：来源、定位、采集时间和置信度，由 ingest 公共字段保存。

## 2. 强制拆分规则

一段材料包含多项陈述时，按以下顺序检查。任一条件成立，就必须拆成不同事实。

1. **可独立变化**：其中一项变化或过期时，其他项仍然成立。
2. **对象不同**：例如人工账号与服务账号、应用与数据库。
3. **范围不同**：例如生产与测试、境内与境外、CDE 与非 CDE。
4. **机制不同**：例如 MFA、堡垒机审计、密钥轮换和备份恢复。
5. **来源不同**：无法由同一个精确来源定位共同支撑。
6. **确认时间或置信度不同**：不能共享同一个事实状态。
7. **责任或维护周期不同**：由不同团队维护，或按不同频率复核。
8. **证据可独立提供**：每项可以由不同配置、日志、截图或记录证明。

连接词“并且”“同时”“以及”不必然要求拆分；它们连接的内容能够独立变化时才拆分。

## 3. 合并规则

只有同时满足以下条件时，多个描述才可以保留在一条事实中：

- 描述同一个对象和范围；
- 来自同一来源定位并共享置信度；
- 按同一生命周期变化；
- 任一部分脱离其他部分后都不足以表达完整、可验证的主张。

例如，“生产运维账号通过企业身份平台登录，登录时必须提供密码和硬件令牌”可以
保留为一条事实，因为入口和认证步骤共同描述同一个认证机制。

## 4. 框架中立要求

系统事实必须描述系统状态，不得写合规判断。标题和正文不得使用“符合”“满足控制”
“通过审核”等结论性表述。

同一事实可以通过 `related_controls` 关联多个框架：

```yaml
related_controls:
  - dengbao-2.0:8.1.4.1
  - iso27001-2022:A.5.17
  - pci-dss-4.0:8.4.2
```

关联只是检索入口，不改变事实语义。某个框架是否满足仍由该项目的 matrix 判断。

## 5. 例外、否定与不确定性

- 例外是主张边界的一部分时，必须写明，不能用“全部”“始终”等词掩盖例外。
- 例外拥有独立机制、来源或变化周期时，必须另拆事实。
- 来源明确证明某措施缺失时，可以记录否定事实，例如“测试环境管理员未启用 MFA”。
- 来源不足时不得把推测写成事实；降低 `confidence`，在正文中限定已知范围，或不输出。
- 测评结论、缺口、整改和例外批准属于 `project_fact` 或 matrix，不得伪装成系统事实。

## 6. Ingest 输出约定

当前 schema 使用 `domain`、`title` 和 `body` 承载语义：

- `domain` 应是稳定的业务分类，例如身份认证、架构、资产、网络、日志、备份。
- `title` 应写成可判真的主张，不使用“身份认证情况”“安全措施”等主题式标题。
- `body` 应先明确对象和范围，再写客观状态、必要机制与例外。
- `external_key` 应标识“来源定位 + 主张语义”，同一来源中的不同原子事实使用不同 key。
- `related_controls` 可以为空或包含多个框架控制，不得为了某个控制复制事实正文。

合规示例：

```json
{
  "kind": "system_fact",
  "external_key": "iam-design:p18:prod-admin-mfa",
  "source": {
    "type": "doc",
    "title": "运维访问管理方案",
    "reference": "iam-design-v2.pdf",
    "locator": "第 18 页",
    "document_date": "2026-07-10"
  },
  "confidence": "high",
  "target": {"system": "order-platform"},
  "content": {
    "domain": "身份认证",
    "title": "生产运维账号使用密码和硬件令牌认证",
    "body": "对象与范围：生产环境人工运维账号。客观状态：账号通过企业身份平台登录，必须同时提供密码和硬件令牌。例外：自动化服务账号不使用该流程。",
    "related_controls": [
      "dengbao-2.0:8.1.4.1",
      "iso27001-2022:A.5.17"
    ]
  }
}
```

自动化服务账号的限制和凭据管理机制应由其他事实描述。

## 7. 粒度示例

过粗的原文：

> 系统启用了 MFA、堡垒机审计、日志告警、数据库备份和季度恢复测试。

应拆为：

| 事实 | 独立变化边界 |
|---|---|
| 生产运维账号启用密码与硬件令牌认证 | 认证策略 |
| 生产运维访问必须经过堡垒机 | 访问路径 |
| 堡垒机记录生产运维会话 | 审计配置 |
| 高风险登录事件触发安全告警 | 监控规则 |
| 生产数据库每日执行增量备份 | 备份计划 |
| 生产数据库备份每季度执行恢复测试 | 恢复演练流程 |

过细的拆分：

```text
用户输入密码
系统校验密码
系统请求硬件令牌
用户提交令牌
```

若这些步骤来自同一配置、覆盖同一账号群体并共同变化，应合并为“生产运维账号使用
密码和硬件令牌认证”。

## 8. 输出前检查清单

Agent 在生成每条 `system_fact` 前必须逐项确认：

- [ ] 只包含一个可独立判真的主张。
- [ ] 对象、系统边界和适用环境明确。
- [ ] 所有内容共享同一来源定位、确认时间和置信度。
- [ ] 任一子句单独变化时，其余内容不会仍然成立；否则已经拆分。
- [ ] 必要例外已经写明，独立例外已经另拆。
- [ ] 标题是客观主张，不是宽泛主题或合规结论。
- [ ] 正文不包含“符合某框架”之类 matrix 结论。
- [ ] `external_key` 对当前原子主张稳定且唯一。
- [ ] 没有为了不同框架或控制项复制同一事实。
- [ ] 不确定内容已限定范围、降低置信度或不输出。

如果任一项无法确认，必须调整拆分或暂停写入，不得直接 apply。

## 9. 与事实演化的关系

粒度边界也是事实的变化边界。未来事实发生变化时，应追加新事实并通过
`supersedes` 建立替代链，而不是覆盖旧事实。拆分得当时，一项机制变化只会替代
对应事实，不会迫使无关系统知识一起失效。
